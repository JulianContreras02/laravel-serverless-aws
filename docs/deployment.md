# Deployment

The application stack is deployed by GitHub Actions with short-lived credentials from GitHub's OIDC provider.
No AWS access keys are stored in GitHub or anywhere else. Setting it up takes three steps: apply the bootstrap
stack once, configure the GitHub environment, then run the workflow.

> This repository is not deployed publicly, to keep the AWS bill at zero. Every part except the AWS apply runs in CI
> (Terraform `fmt`/`validate`, the Lambda package build). The packaged zip was also tested locally in Bref's Lambda
> emulator, through both the FPM and the console runtimes.

## 1. Bootstrap (once, by an administrator)

[`infra/bootstrap`](../infra/bootstrap) creates:

| Resource | Purpose |
|---|---|
| S3 bucket `shortlinks-tfstate-<account id>` | Remote state: versioned, encrypted, TLS-only, public access blocked. Locking uses S3 conditional writes (`use_lockfile`), so there is no DynamoDB table. |
| IAM OIDC provider `token.actions.githubusercontent.com` | Lets GitHub Actions exchange its job token for AWS credentials. An account can only have one; pass `-var create_github_oidc_provider=false` if it exists. |
| IAM role `shortlinks-github-deploy` | The role the workflow assumes. |
| IAM policy `shortlinks-workload-boundary` | Permissions boundary that every role created by the deploy role must carry. |

Run it with administrator credentials in your shell. Terraform does not need to be installed; Docker is enough:

```bash
cd infra/bootstrap
docker run --rm -it -v "$PWD:/w" -w /w -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_SESSION_TOKEN hashicorp/terraform:1.17 init
docker run --rm -it -v "$PWD:/w" -w /w -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_SESSION_TOKEN hashicorp/terraform:1.17 apply
```

Keep the resulting `terraform.tfstate` safe (it holds no secrets). Note the outputs `deploy_role_arn` and `state_bucket`.

### What the deploy role can and cannot do

- **Trust:** only tokens whose `sub` is `repo:JulianContreras02/laravel-serverless-aws:environment:production` and
  whose audience is `sts.amazonaws.com`. Other repositories, forks and jobs outside the `production` environment are
  refused.
- **Scope:** create and manage resources whose names start with `shortlinks-` (Lambda, API Gateway, RDS, log groups,
  alarms, dashboard, SNS, scheduler, IAM roles) in one region, plus read the Bref layers and the state objects.
- **No privilege escalation:** it can create IAM roles only if they carry the `shortlinks-workload-boundary`
  permissions boundary. The boundary allows logs, VPC network interfaces and invoking `shortlinks-*` functions. The
  role cannot remove a boundary.
- **Not verified against a live account.** The policy was written from the AWS service authorization reference. If
  an apply fails with `AccessDenied`, the error names the missing action. Add it to
  [`infra/bootstrap/main.tf`](../infra/bootstrap/main.tf), scoped like its neighbours, and apply the bootstrap again.

## 2. GitHub configuration

In **Settings → Environments**, create `production` with:

- **Required reviewers**: you. Every apply then waits for an approval.
- **Deployment branches**: `main` only. This matters: the role trusts the environment, not the branch, so this rule
  is what stops a deploy from another branch.

Variables (environment or repository level):

| Variable | Value |
|---|---|
| `AWS_REGION` | `us-east-1` (must match the bootstrap) |
| `AWS_DEPLOY_ROLE_ARN` | bootstrap output `deploy_role_arn` |
| `TF_STATE_BUCKET` | bootstrap output `state_bucket` |

Optional secret: `ALARM_EMAIL`, an address subscribed to the alarm topic (confirm the e-mail AWS sends). It is a
secret rather than a variable because Actions logs of a public repository are public.

With the GitHub CLI:

```bash
gh variable set AWS_REGION --env production --body us-east-1
gh variable set AWS_DEPLOY_ROLE_ARN --env production --body arn:aws:iam::123456789012:role/shortlinks-github-deploy
gh variable set TF_STATE_BUCKET --env production --body shortlinks-tfstate-123456789012
gh secret set ALARM_EMAIL --env production
```

## 3. Deploy

**Actions → Deploy → Run workflow** on `main`.

1. Leave **apply** unchecked the first time: the job builds the zip, assumes the role and runs `terraform plan`.
   The plan summary appears on the run page.
2. Run it again with **apply** checked. The job applies the plan, runs `php artisan migrate --force` on the Artisan
   function (and fails if the command fails) and calls `/health`.

The first apply takes about 10 minutes, mostly RDS. The API URL is in the job summary.

### First link

The management token was generated by Terraform. Read it with credentials that can read the state:

```bash
cd infra/app
terraform init -backend-config="bucket=<state bucket>" -backend-config="key=shortlinks/prod.tfstate" -backend-config="region=us-east-1"
terraform output -raw api_token
```

```bash
curl -X POST "$API_URL/api/links" \
  -H "Authorization: Bearer $API_TOKEN" -H "Content-Type: application/json" \
  -d '{"url": "https://example.org", "alias": "hello"}'
```

## Rollback

Run the workflow on the previous commit or tag (**Run workflow → Use workflow from**). Migrations only add tables and
columns, so the previous code runs fine against the newer schema. A destructive schema change would need its own
two-step release (expand, then contract).

## DORA metrics

Every run of the deploy job is a GitHub deployment of the `production` environment, so the data for two of the four
DORA metrics is already recorded:

- **Deployment frequency** and **lead time for changes**: `gh api repos/JulianContreras02/laravel-serverless-aws/deployments`
  lists each deployment with its commit, and the commit date gives the lead time.
- **Change failure rate**: failed or rolled-back deploy runs over total runs.
- **Time to restore**: the time between an alarm entering `ALARM` and returning to `OK` (CloudWatch alarm history).

## Tearing down

1. Set `db_deletion_protection = false` and run the workflow with apply. Then, locally with administrator
   credentials, build the zip (Terraform hashes it even to destroy) and destroy:
   `scripts/package-lambda.sh && terraform -chdir=infra/app destroy -var bref_layer_version=$(cat build/bref-layer-version)`.
2. RDS keeps a final snapshot (`shortlinks-prod-final`); delete it by hand if you do not need it.
3. Lambda network interfaces in the VPC can take up to an hour to be released, which can make the VPC deletion wait.
4. The state bucket has `prevent_destroy`; remove that line before destroying the bootstrap stack.
