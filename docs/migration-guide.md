# Migration guide: legacy PHP → Laravel on AWS Lambda

How the plain-PHP shortener in [`legacy/`](../legacy) became this service, and the order I follow when doing
the same for a client's application. The goal is to keep the URLs and the data, and change everything behind them.

## What changed, problem by problem

| # | Legacy ([`legacy/`](../legacy)) | Now | Why |
|---|---|---|---|
| L1 | Credentials hardcoded in `config.php` | Environment variables; in AWS, generated by Terraform | Secrets never enter git, and each environment has its own |
| L2 | Routing in `.htaccess` | API Gateway `$default` route → Laravel router | No web server to configure; routes are code and are tested |
| L3 | SQL built by concatenation | Query builder and Eloquent with bindings | Injection-safe by construction, not by remembering to escape |
| L4 | `UPDATE links SET hits = hits + 1` per click | Append-only `clicks` table | No hot row: concurrent visitors of a viral link do not wait on each other |
| L5 | Stats grouped from raw clicks on each view | `link_daily_stats` rebuilt every 5 minutes | Reads cost the same at 1M clicks as at 100 ([benchmarks](benchmarks.md)) |
| L6 | Log file on the server's disk | Structured logs on stderr → CloudWatch | Lambda's disk is ephemeral and per instance; logs must leave it |
| L7 | Admin session files on disk | Stateless bearer token | Requests can land on any Lambda instance |
| L8 | `crontab` on the server | EventBridge Scheduler → `schedule:run` → `routes/console.php` | Scheduled work is versioned, deployed with the code and monitored |
| L9 | No tests; deploy by copying files | CI on every push; manual OIDC deploy with plan, migrations and smoke test | A change is checked before it reaches users, and every deploy is recorded |
| L10 | `301` redirect | `302` with `Cache-Control: no-store` | Browsers cache 301s forever: later clicks vanish and disabling a link does nothing |
| L11 | Case-insensitive collation on `code` | `ascii_bin` collation | `aB3x` and `ab3x` were the same link; now they are distinct codes |
| L12 | `md5(rand())` and check-then-insert | `random_int` base62 + unique index + retry | No duplicate codes under concurrency |

Privacy improved on the way: the legacy app stored full referrer URLs and visitor IPs forever. Now only the referrer
host is kept, there is no IP, and raw clicks expire after 90 days.

## The order I follow

1. **Inventory before code.** List every entry point (URLs, forms, webhooks), every scheduled job, everything written
   to disk (uploads, logs, sessions, caches, reports), outbound calls, required PHP extensions, and the slowest and
   largest requests. Lambda stops at 15 minutes, API Gateway at 30 seconds, and a synchronous invocation carries
   about 6 MB per request and response, so anything near those limits needs its own design up front.
2. **Pin the current behavior with tests.** Write HTTP tests against the legacy behavior that must survive (status
   codes, redirect targets, error pages). They become the first tests of the new code; here, that is the role of
   `tests/Feature/RedirectTest.php`.
3. **Remove local state.** Disk becomes S3 or the database, sessions become tokens or a shared store, logs go to
   stderr, and `crontab` becomes the scheduler. This step is what makes horizontal scaling possible, on Lambda or
   anywhere else.
4. **Port the routes, keeping the URLs.** Short links already printed on paper or shared in chats must keep working.
   Migrations adopt the existing schema and only add: new tables, columns and indexes, never destructive changes in
   the same release.
5. **Infrastructure as code and CI before the first deploy**, so the first production deploy is the hundredth
   rehearsal and not the first.
6. **Move the data.**
   - Convert timestamps to UTC: legacy `NOW()` used the server's local time zone (`CONVERT_TZ(clicked, 'America/Bogota', '+00:00')`).
   - Look for codes that differ only by case (`GROUP BY LOWER(code) HAVING COUNT(*) > 1`) before switching to a
     binary collation, and decide which one wins.
   - Reduce referrers to hosts and drop IPs while copying `clicks`.
   - Rebuild the aggregates with `php artisan stats:rollup --days=90`.
7. **Cut over with a way back.** Lower the DNS TTL a day before, switch the domain to API Gateway, and keep the old
   server read-only for a few days so you can go back if needed.

## Lambda-specific traps

- **The filesystem is read-only** except `/tmp`, and `/tmp` is per instance and temporary. The Bref bridge moves
  Laravel's storage there; anything that must persist goes to S3 or the database.
- **In-memory and file caches are not shared.** Each instance has its own and new instances start empty. Rate
  limiting, locks and tokens that must be shared need a shared store; here the cache store is the database.
- **Stale caches after a deploy.** A route cache built on a developer machine ships old routes (a new route answers
  404). Here the deploy builds the route cache fresh every time, and the config is cached by Bref on each cold start.
- **A VPC without a NAT gateway has no internet.** That is cheap and safe until the code needs an AWS API or a third
  party. Plan the egress (NAT gateway, VPC endpoints, or functions outside the VPC) before adding such a call, and
  look at the cost table in the README.
- **Connections scale with concurrency.** Every Lambda instance opens its own database connection. Cap concurrency
  (`web_reserved_concurrency`) or put RDS Proxy in front before a traffic spike exhausts `max_connections`.
